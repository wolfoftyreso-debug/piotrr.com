# System Audit — July 2026

Scope: the M1 codebase (Next.js monolith, Foundation Prompt v1.1), with focus
on account and company creation flows ("think Alibaba" — self-serve entry for
both sides of the marketplace).

## Method

- Static review of modules, services, RBAC guards and API routes
- 25 unit tests (state machines, expiry engine, RBAC, rate limiter)
- Full-database smoke test (`npx tsx src/db/smoke.ts`) against Postgres 16
- Live production-build test: server started, endpoints exercised with curl

## Findings and resolutions

| # | Finding | Severity | Resolution |
|---|---------|----------|------------|
| F1 | **Customers could not be created at all** — users existed only via seed; no registration page or API | Blocker | Fixed: `/register` page (buyer/supplier choice, sv/en/lt), `registerUser` service with audit + outbox, `POST /api/v1/auth/register` (Zod, Idempotency-Key, rate limited). Self-serve can only create `buyer`/`supplier` roles — never `admin`/`ops` |
| F2 | **Companies could only be created by ops** — suppliers had no way to register their own company | Blocker | Fixed: suppliers create exactly one company (ownership via `owner_user_id`); ops concierge flow unchanged. Enforced in the service layer, not only UI |
| F3 | **Supplier/buyer accounts had no surface** — sign-in redirected everyone to `/admin`, non-ops bounced to the landing page | High | Fixed: `/portal` (thin self-service per M2): suppliers create/see their company, follow verification requirement statuses, manage workers; buyers get their account surface (RFQ intake arrives with M3). `/go` routes each role after login |
| F4 | **Self-registered suppliers were invisible to ops** — no signal to open a verification case | High | Fixed: `companies.created {selfServe:true}` outbox event → dispatcher creates an ops task ("review and open verification case"), keeping module boundaries intact |
| F5 | **No rate limiting on public endpoints** (Section 4.7) — became acute with public registration | Medium | Fixed: fixed-window limiter (in-memory, correct for the one-container stage) on registration API + server action; unit tested |
| F6 | Supplier-scoped mutations (`addWorker`) did not check company ownership | Medium | Fixed: suppliers can only manage their own company (service-layer check, covered by smoke test) |
| F7 | Contacts existed in schema/UI but nothing could create them | Low | Fixed: add-contact form in the company 360° view + `addContact` service with ownership guard |
| F8 | `companies.ownerUserId` was never populated | Low | Fixed via F2 |

## Verified working (evidence)

- Buyer registration → account created, password stored as scrypt hash,
  duplicate email rejected (smoke §9–10; live curl 201 + replay via
  Idempotency-Key returned the same body)
- Supplier registration → own company created, one-company rule enforced,
  foreign-company access blocked, buyer blocked from creating companies
  (smoke §11–14)
- Outbox → ops task for self-registered supplier (smoke §15)
- M1 core unchanged and still green: case/item state machines, expiry engine
  with simulated clock, badge derived only from case state, audit trail
- `/api/healthz` ok; unauthenticated `/api/v1/companies` correctly 403;
  register pages render in sv/en/lt (HTTP 200)
- Lint, typecheck, 25 unit tests and production build all clean

## Compliance notes (Foundation Prompt v1.1)

Self-serve supplier/buyer entry is pulled forward from M2/M3 in *thin* form
(the foundation assigns supplier self-service to M2 and buyer accounts to
M3); the ops concierge flow remains primary and verification stays entirely
ops-driven and binary. No new dependencies were added.
